# Current setup (bokxcms.next)

This document captures the **current runtime/build setup** of this repo: tech stack, CMS integration, database selection, and how images/media are stored and served.

## Tech stack

- **Framework**: Next.js `16.2.6` (App Router) (`package.json`)
- **UI**: React `19.2.4`, React DOM `19.2.4` (`package.json`)
- **CMS**: Payload `^3.85.0` with `@payloadcms/next` integration (`package.json`, `next.config.ts`, `src/app/layout.tsx`)
- **DB adapters**:
  - `@payloadcms/db-sqlite` for local/dev by default
  - `@payloadcms/db-vercel-postgres` for Vercel/Neon/Postgres
- **Media processing**: `sharp` is configured in Payload (`payload.config.ts`)
- **Styling**: Tailwind CSS `^4` (`package.json`)
- **Language/tooling**: TypeScript `^5`, ESLint `^9` (`package.json`)

## App structure (high-level)

- **Next app root**: `src/app/`
- **Payload “route group”**: `src/app/(payload)/`
  - REST API routes are mounted under `src/app/(payload)/api/[...slug]/route.ts` (generated by Payload)
  - Payload admin uses `src/app/(payload)/admin/...` (generated/scaffolded pieces)
- **Payload config**: `payload.config.ts`
- **Payload collections**: `src/payload/collections/*`
  - `Users`, `Posts`, `Media`

## Payload + Next integration

- `next.config.ts` wraps Next config via `withPayload(...)`.
- `src/app/layout.tsx` uses Payload’s `RootLayout` and wires server functions via `handleServerFunctions(...)`.
- `tsconfig.json` defines the alias `@payload-config` → `./payload.config.ts`.

## Database selection (SQLite vs Postgres)

Payload chooses the DB adapter in `payload.config.ts` via `shouldUsePostgres()`:

- **Postgres is used when**:
  - `VERCEL=1`, or
  - `POSTGRES_URL` is set, or
  - `DATABASE_URL` starts with `postgres://` or `postgresql://`
- **SQLite is used otherwise**:
  - Defaults to `DATABASE_URL=file:./payload.db` (fallback is `file:./payload.db`)

### Schema management / “push” behavior

- **Postgres adapter `push`** defaults to:
  - enabled for non-production non-Vercel (convenience), or
  - can be forced with `PAYLOAD_DB_PUSH=true`
- **SQLite adapter `push`** is **off by default** and can be enabled with `PAYLOAD_SQLITE_PUSH=true`

This is intended to avoid schema push issues in existing SQLite DBs and to prevent unintended pushes in Vercel environments.

## Media + image serving

There are two distinct “image” flows in this repo:

### 1) Payload `media` collection (uploads)

- The `media` collection is configured in `src/payload/collections/Media.ts` with `upload: true`.
- **Local/dev storage**:
  - When using SQLite (typical local dev), Payload stores uploads on the local filesystem.
  - This repo already contains a top-level `media/` directory, which is consistent with local upload storage being present.
- **Vercel/production storage (Blob)**:
  - When Postgres is selected, `payload.config.ts` enables `@payloadcms/storage-vercel-blob` for `media`.
  - Requires `BLOB_READ_WRITE_TOKEN`.
  - Admin uploads use the Blob client upload handler wired via `src/app/(payload)/admin/importMap.js`.

**Implication**: In Postgres/Vercel mode, uploaded images are backed by **Vercel Blob** (and referenced from Postgres). In SQLite/local mode, uploads are local.

### 2) Dropbox ingestion → Payload media

The repo includes Dropbox APIs to ingest images from a Dropbox folder into Payload:

- **Endpoints**
  - `POST /api/dropbox/sync`: downloads image files from Dropbox and:
    - creates a `media` upload in Payload
    - creates or updates a `posts` document and links `posts.image` to the created `media`
  - `GET /api/dropbox/folder`: lists a Dropbox folder (see `src/app/api/dropbox/folder/route.ts`)
  - `GET /api/dropbox/file?path=...`: downloads a Dropbox file and returns its content (mostly for inspection/debugging)
- **Post model linkage**
  - `src/payload/collections/Posts.ts` has:
    - `image`: `upload` relation to `media`
    - `dropbox` group fields to track the source file (`pathLower`, `id`, `rev`)

This provides a repeatable path for **sourcing images from Dropbox**, storing them in Payload `media`, and attaching them to `posts`.

## Build and deploy

- **Local dev**: `npm run dev` → `next dev`
- **Build**: `npm run build` runs `node scripts/build.mjs`
  - Always runs `next build`
  - On Vercel (`VERCEL=1`), it **optionally runs** `payload migrate`:
    - runs when `POSTGRES_URL` is set, or when `PAYLOAD_FORCE_MIGRATE=1`
    - otherwise it logs a warning and continues the build
- **CI script**: `npm run ci` runs `payload migrate && next build`

## Operational scripts (Payload bin)

`payload.config.ts` registers additional bin scripts (usable via `payload <key>` / `npx payload <key>` or via the npm scripts in `package.json`):

- `export:sqlite` → `scripts/bin/export-sqlite.cjs`
- `migrate:media:blob` → `scripts/bin/migrate-media-to-blob.cjs`
- `import:neon` → `scripts/bin/import-to-neon.cjs`
- `verify:neon` → `scripts/bin/verify-neon.cjs`

See `MIGRATION_HANDOFF.md` for the intended SQLite → Postgres/Blob workflow.

## Environment variables (expected)

### Payload / DB

- `PAYLOAD_SECRET`
- `DATABASE_URL`
  - SQLite: `file:./payload.db`
  - Postgres: `postgres://...` / `postgresql://...`
- `POSTGRES_URL` (strongly preferred/required for Vercel Postgres integration)
- `PAYLOAD_DB_PUSH` (optional; `"true"` to allow schema push)
- `PAYLOAD_SQLITE_PUSH` (optional; `"true"` to allow schema push on SQLite)

### Vercel Blob (when Postgres mode)

- `BLOB_READ_WRITE_TOKEN`

### Dropbox integration

- `NEXT_PUBLIC_DROPBOX_APP_KEY`
- `DROPBOX_APP_SECRET`
- `DROPBOX_ACCESS_TOKEN` (required for calling Dropbox API routes)
- `DROPBOX_REFRESH_TOKEN` (if using refresh-token flows)
- `DROPBOX_FOLDER_PATH` (default folder path for sync/list)
- `DROPBOX_EXAMPLE_FILE_PATH` (optional; used by the homepage example)
